# Правила проекта

## Язык

Проект публичный, поэтому всё, что видит кто-либо кроме меня, пишется
по-английски. Правило касается любого файла и любого текста.

1. Английский обязателен для:

   - комментариев в коде;
   - сообщений об ошибках и журнала;
   - текстов интерфейса (кроме каталога перевода `ru`);
   - README, документации, инструкций;
   - описаний инструментов в манифестах плагинов - их читает модель;
   - сообщений коммитов и описаний релизов;
   - названий и описаний плагинов.

2. Русский допустим только в двух местах:

   - файлы перевода в `ru` - для русских пользователей;
   - общение со мной в чате.

3. Идентификаторы, имена файлов и пути всегда латиницей, независимо от
   языка текста рядом.

4. Исключение - данные для проверки самого механизма перевода: в тестах
   нужен текст на другом языке, чтобы отличить перевод от оригинала. Такой
   текст должен быть помечен комментарием.

## Комментарии

1. Комментарий описывает функцию - что делает код. А не то, что мы сделали
   на данный момент. Истории изменений в комментариях быть не должно:
   никаких «добавили», «поправили», «переделали», «раньше было так»,
   «теперь работает иначе».

2. Коротко. Обычно достаточно одной строки. Больше - только если без этого
   смысл действительно непонятен.

3. Не пересказывай очевидное из кода. Если по самому коду всё ясно,
   комментарий не нужен.

4. Если что-то сложное - не расписывай это в комментарии, а напиши
   объяснение в чат отдельным сообщением.

5. Тире только короткое: "-". Длинное тире "—" не использовать.
   Это правило касается всего текста, а не только комментариев.

6. Касается любого кода в проекте: Go, JS, CSS, HTML и др.

## Логирование

1. Каждое сообщение начинается с тега в квадратных скобках: "[Web] ...".
   Тег - одно слово, которое указывает, к чему относится лог: модуль,
   подсистема или область. Примеры: "[App]", "[Web]", "[Config]", ... .

2. Тег пишется в начале сообщения, отдельного аргумента для него нет.
   Пробелы внутри тега допустимы только когда одного слова мало:
   "[Some Manager]", "[Some Engine]".

3. Постоянный тег для модуля: одно и то же место всегда пишет один и тот
   же тег. Свой вариант тега для одного и того же модуля не придумывать.

4. Если сообщение относится к конкретному объекту, тег уточняется через
   двоеточие без пробела: "[Some:tester]", "[Other:admin]". Уточнение -
   это ID, имя или логин, а не произвольный текст.

5. Уровень выбирается по смыслу:
   - Debug - подробности для разработки, которых нет в обычном режиме;
   - Info - обычные значимые события: старт, остановка, успешная операция;
   - Warn - неожиданное, но не ломающее работу: отказ, пропуск, дефолт;
   - Error - операция не выполнена, нужна реакция.

6. Сообщения на английском языке. Текст - с заглавной буквы, без точки
   в конце. Тег всегда латиницей.

7. Сообщение описывает событие, а не адрес в коде: не "in function
   loadConfig", а "failed to load config".

8. Значения передаются параметрами и форматированием ("%s", "%v"),
   а не склейкой строк. Ошибку добавлять в конец: "...: %v".

9. Формат строки задает логгер, а не вызывающий код: время, уровень и
   стек добавляются автоматически, дублировать их в сообщении не нужно.

10. Сообщение не должно содержать секретов: паролей, токенов, ключей.

## Архитектура и процесс разработки

1. Проект строится по микроядерной архитектуре: ядро отвечает только за
   базовую инфраструктуру (IPC, шина событий и хуков, хранилище, рантайм
   плагинов, цикл сессии), а вся прикладная функциональность реализуется
   отдельными плагинами из каталога `plugins/`.

2. Плагины не вшиваются в бинарник ядра. Базовые плагины хранятся в
   репозитории в `plugins/` и устанавливаются отдельно через `make install`.

3. Перед началом любой разработки обязательно сверяться с:
   - `ARCHITECTURE.md` - устройство системы, модули, контракты плагинов;
   - `PLUGINS.md` - структура плагинов, формат `manifest.json` и справочник API объекта `cdx`;
   - `ROADMAP.md` - пошаговый план реализации и текущий прогресс.

4. Разработка ведется строго по стадиям из `ROADMAP.md`:
   - выполнять одну стадию (или подзадачу) за раз;
   - покрывать новый код модульными тестами (`go test ./...`);
   - проверять код анализатором (`go vet ./...`);
   - после завершения стадии отмечать прогресс в `ROADMAP.md`.

5. Если в процессе реализации требуется изменить архитектуру или контракты,
   сначала обновляется `ARCHITECTURE.md` по согласованию с автором проекта.

6. Новые аргументы, флаги и подкоманды CLI, а также изменения существующих,
   сначала согласуются с автором проекта. Нельзя добавлять аргументы «на
   будущее» или менять их смысл без явного запроса.
